# MindSync VR React Native

MindSync VR is the mobile orchestration layer for the adaptive VR meditation research system. This React Native CLI application coordinates the ESP32-S3 wearable, backend adapters, Unity/VR handoff, participant onboarding, session safety controls, Component D validation, and session analytics.

The original Kotlin application remains in the repository root as a migration reference. New mobile development should target this directory.

## Stack

- React Native 0.87.1 and TypeScript
- React Navigation native stack and bottom tabs
- Zustand with AsyncStorage persistence
- TanStack Query for server-state retries and caching
- Android Keystore/iOS Keychain token storage through `react-native-keychain`
- Supabase Auth and PostgreSQL with row-level security
- `react-native-ble-plx` for native BLE
- React Hook Form and Zod
- Reanimated and Worklets for restrained motion
- React Native SVG for charts
- Native module boundary for future Unity embedding

React Native CLI was selected instead of Expo because BLE, Unity embedding, microphone capture, and research-device integration require direct ownership of Android/iOS native projects.

## Setup

Requirements:

- Node.js 22.11 or newer
- JDK 17 or newer
- Android Studio with Android SDK and NDK
- A physical Android phone for BLE testing

Install packages:

```bash
cd react-native-app
npm install
```

`npm install` also generates the local TypeScript environment module. The
generated file and `.env` are ignored by Git.

Create `android/local.properties` if Android Studio has not created it:

```properties
sdk.dir=/Users/your-name/Library/Android/sdk
```

Run in development:

```bash
npm start
```

In another terminal:

```bash
npm run android
```

## Supabase Setup

The app runs in explicit demo mode when Supabase is not configured. To enable
real authentication and database persistence:

1. Create a Supabase project.
2. Open the Supabase SQL editor and run:

   ```text
   supabase/migrations/202609010001_initial_mobile_schema.sql
   ```

   Alternatively, link this folder with the Supabase CLI and run `supabase db
   push`.
3. Copy `.env.example` to `.env` and set the project URL and publishable key:

   ```dotenv
   SUPABASE_ENABLED=true
   SUPABASE_URL=https://your-project-ref.supabase.co
   SUPABASE_PUBLISHABLE_KEY=sb_publishable_replace_me
   ```

4. In Supabase Authentication, enable Email authentication. Decide whether the
   research deployment requires email confirmation before inviting
   participants.
5. Rebuild the app so the configuration is bundled:

   ```bash
   npm run typecheck
   npm run android
   ```

Only use the Supabase publishable key (or legacy anon key) in `.env`. Never put
the `service_role` key, database password, or another privileged secret in a
mobile build. The publishable key is intentionally treated as public; access is
enforced by the authenticated participant session and PostgreSQL row-level
security.

The migration creates:

- `profiles`: participant identity and onboarding state
- `onboarding_profiles`: personalization and current consent choices
- `participant_consents`: append-only privacy and research consent events
- `meditation_sessions`: session history and outcome metadata
- `questionnaire_submissions`: Component D response objects stored as JSONB
- `wearable_devices`: device registration metadata and last connection time
- `complete_session_records`: combined voice and finalized VR visual records

Every exposed table has row-level security. Participants can access only rows
owned by their Supabase Auth user ID. Consent events allow insert and read only;
the mobile role cannot edit or delete their audit history.

Supabase sessions are persisted in Android Keystore/iOS Keychain and refreshed
only while the app is active. The app restores the authenticated profile before
showing protected routes. Questionnaire and complete-session records are saved
to the existing local outboxes first, then uploaded on login, manual sync, or
after session completion. The Settings screen reports synchronized, offline,
and error states.

Raw PPG samples are intentionally not inserted into Supabase. They continue over
the low-latency BLE -> Component B WebSocket path. Supabase stores participant,
session, consent, and validation records; a future server-side archival policy
can store derived Component B outcomes without exposing a high-rate database
write endpoint in the mobile client.

## Wearable BLE Contract

The app matches the firmware in:

```text
../firmware/esp32_s3_wearable_health_monitor/esp32_s3_wearable_health_monitor.ino
```

- Device name: `WearableHealthMonitor`
- Service: `7c69f001-7f70-4b0a-9c91-93d7f91b1001`
- Telemetry characteristic: `7c69f002-7f70-4b0a-9c91-93d7f91b1001`
- Raw PPG characteristic: `7c69f003-7f70-4b0a-9c91-93d7f91b1001`
- Properties: read and notify
- UI telemetry rate: approximately 5 Hz
- Raw PPG rate: five timestamped samples per binary notification, approximately 20 notifications/s at the MAX30100's 100 Hz acquisition rate

Current packet:

```json
{"t":1097073,"ir":24500,"red":43000,"noiseAvg":85000,"noisePeak":180000,"temp":null,"flags":3}
```

`temp` is currently `null` because the wearable temperature sensor is unavailable. The parser also accepts future compact fields `hr`, `rr`, `spo2`, and `bat`. Missing device measurements remain `null`; the firmware and mobile UI do not relabel generated data as a sensor reading.

The raw PPG characteristic is fixed-width, binary, and little-endian. Its 41-byte packet layout is:

| Offset | Size | Field |
| --- | ---: | --- |
| 0 | 1 | Valid sample count, 1 through 5 |
| 1 + n*8 | 4 | Sample `n` ESP32 uptime in milliseconds, unsigned 32-bit |
| 5 + n*8 | 4 | Sample `n` raw IR amplitude, unsigned 32-bit |

Only the first `sample_count` slots are valid. Remaining slots are zero-filled and ignored. The app requests MTU 185 before subscribing, validates all packets, handles the ESP32 uptime rollover, and discards partial research frames when acquisition gaps are detected.

Android scanning is intentionally unfiltered at the scanner level. Some phones omit the ESP32 name and service UUID from scan callbacks. Verified advertisements are ranked first; strong anonymous candidates can be selected, but the app reports Connected only after discovering the exact service and notifiable telemetry characteristic.

## Android and iOS Permissions

Android declares legacy Bluetooth/location permissions through Android 11 and `BLUETOOTH_SCAN`/`BLUETOOTH_CONNECT` for Android 12+. Runtime permission requests live in the BLE service. Microphone and network permissions are reserved for Component D.

iOS `Info.plist` includes Bluetooth, microphone, local-network, and legacy location usage descriptions. Run CocoaPods before an iOS build:

```bash
cd ios
bundle install
bundle exec pod install
```

## Component B Live Pipeline

Component B already exposes the `/ingest` WebSocket and remains the only process that derives RR intervals, HRV, and stress. The mobile app performs transport framing only:

```text
MAX30100 100 Hz FIFO
  -> raw PPG BLE batches
  -> safe little-endian parser
  -> timestamp-aware linear resampling to 64 Hz
  -> 960-sample / 15-second frame
  -> Component B ws://<host>:8000/ingest
```

The outbound shape is shown below with the PPG array abbreviated:

```json
{"timestamp":1787282838.4,"sample_rate":64.0,"ppg":[1834.2,1836.1],"temperature":33.7}
```

The real `ppg` array always contains exactly 960 finite amplitudes. `timestamp` is the frame start in POSIX seconds. The app sends `temperature: null` while the physical sensor is unavailable. Component B resolves that field to a smooth, bounded synthetic body-surface value and labels the acknowledgement `temperature_source: synthetic_backend`. The app never fills missing PPG data by repeating the latest UI telemetry value; a raw-sample discontinuity resets the partial frame.

Start Component B from the repository root:

```bash
cd component-b
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
# macOS only
brew install libomp
PYTHONPATH=src uvicorn server.main:app --host 0.0.0.0 --port 8000
```

For a USB-connected Android phone, keep the default endpoint and forward the port:

```bash
adb reverse tcp:8000 tcp:8000
```

For a standalone phone on Wi-Fi, open Wearable detail and set the Component B endpoint to `ws://<laptop-LAN-IP>:8000/ingest`. The phone and backend must be on the same network and the laptop firewall must permit TCP port 8000. Internal Android research builds allow local cleartext WebSockets; production distribution must use `wss://` and disable cleartext traffic.

The wearable detail screen reports raw samples buffered, frames sent, backend acknowledgements, resolved temperature/source, reconnect state, and backend errors separately. Component B responds with `accepted`, `invalid_batch`, or `model_unavailable`; an invalid frame does not close the socket.

## Component D

Questionnaire templates support branching, session-linked responses, local completion state, and the export-ready `component-d-v1` response shape. Submissions are persisted with `synced: false` until the real backend sync manager is enabled.

The voice flow preserves the current branch's pre/environment/VR/post/report stages and checks Component D health through `src/services/api/componentDService.ts`. Native microphone recording and server voice-turn transport still need to be ported from the Kotlin `AudioRecord` implementation before voice inference is production-complete; the UI does not fabricate voice analysis results.

For a USB-connected Android phone during local Component D development:

```bash
adb reverse tcp:8010 tcp:8010
```

## Unity Integration

`src/services/unity/unityBridge.ts` is the stable JavaScript API for Unity. It detects an optional `MindSyncUnityBridge` native module and no-ops safely until the Unity Android library is added. The intended next step is to export Unity as an Android library, register the native module, and implement session attach, telemetry forwarding, pause, and stop methods without changing screens or store code.

## Verification

```bash
npm run typecheck
npm test -- --runInBand
npm run lint
```

Physical BLE test:

1. Flash and power the ESP32-S3 firmware.
2. Install the standalone APK on an ARM64 Android phone.
3. Open MindSync VR and log in with the prefilled demo account.
4. Open Wearable, grant Bluetooth permissions, and scan.
5. Select `WearableHealthMonitor`, or the strongest anonymous candidate when Android hides its advertisement.
6. Confirm Connected and live IR, RED, noise average, and noise peak values.
7. Confirm device temperature remains `Unavailable` and Component B temperature is labeled `synthetic backend`.
8. Confirm Raw BLE stream is Available and the Component B frame counter advances to 960.
9. After about 15 seconds, confirm Frames sent and Accepted both increase.
10. Power off the wearable and confirm graceful BLE and Component B reset/reconnect behavior.

`npm audit` currently reports advisories through React Native's Metro `image-size` build dependency. The automatic forced fix proposes downgrading core React Native and is therefore not applied. Recheck this when the matching React Native/Metro patch release is available.
